# JARVIS-X Vegeto Architecture

## Identity rule

JARVIS-X is one coherent executive identity. The Vegeto analogy means fusion into one identity, not a council of models, a provider picker, or competing assistants.

The executive owns the objective, task decomposition, capability selection, policy checks, evidence interpretation, challenge pass, synthesis, and final response. Lead, challenge, and synthesis are internal passes of the same identity. They are not independent model votes.

The configured reasoning runtime is an implementation detail. It does not define JARVIS-X's identity. Image generation, search, memory, coding, browser interaction, and connectors are capabilities invoked under the executive's control; they are never alternate reasoning routes.

## Execution flow

`USER OBJECTIVE -> EXECUTIVE KERNEL -> CAPABILITY POLICY -> APPROVED TOOL -> RECEIPT -> OUTPUT VALIDATION -> WORLD-STATE CHECK -> ONE JARVIS-X RESPONSE`

## Capability rules

Every capability must declare:
- Stable ID and version, purpose, strict input/output schema.
- Data classification, retention, and consent requirements.
- User scopes, consequence level, and approval requirements.
- Cost class, daily/per-request ceilings, and zero-cost eligibility.
- Timeout, concurrency, payload, and retry limits.
- Execution location and credential boundary.
- Receipt schema and tests for denial, malformed input, timeout, duplicate request, capability error, and output validation.

The registry is sealed after construction. The JARVIS-X executive may invoke only registered capabilities. Tool output and retrieved content are untrusted data, never instructions or permission grants.

## Image generation

Nano Banana 2.1 is integrated as an image-generation capability through Google's documented Gemini Interactions API. It is not a second assistant and does not participate in reasoning.

- Model: `gemini-nano-banana-2.1`.
- Server-side credential only; never expose API keys to the browser.
- One image per request, explicit user cost confirmation, bounded prompt and output bytes.
- Atomic image-specific daily budget reservation before any image API call.
- Budget tables are server-only and default to disabled with a zero daily limit.
- Failed requests retain their reservation conservatively; no automatic retry.
- Generated bytes are returned to the current page and are not persisted by the gateway. The user must save the image if they want to keep it.
- API pricing is variable; the published standard 1K image price is approximately USD 0.0336. There is no free API tier for Nano Banana 2.1. Recheck official pricing before activation.

Official references:
- https://ai.google.dev/gemini-api/docs/image-generation
- https://ai.google.dev/gemini-api/docs/pricing

## Portable continuity

Portable export/import is the cross-platform handoff mechanism. It is not automatic cross-device synchronization, and an exported packet is untrusted context rather than authority. The user can review and move it between supported platforms manually.

## Evidence gates

Use these states precisely:

`PROPOSED -> AVAILABLE -> AUTHORIZED -> INVOKED -> EXECUTED -> OUTPUT_VALIDATED -> WORLD_STATE_VERIFIED`

An available adapter is not an invoked adapter. A successful mock test is not a live API test. A successful CI run is not a deployment. A response receipt is not proof of an external world-state change.

## Current source boundary

- Single executive route is enforced by the v12 router source.
- Nano Banana adapter, route, and atomic budget migration are source-integrated.
- Image generation remains disabled by default; the budget migration is not applied to production.
- Live executive inference, live image generation, and production deployment remain unverified.
- Cross-platform portable export/import is local functionality; automatic cross-device sync is not claimed.
